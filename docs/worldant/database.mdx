Worldant uses one PostgreSQL data plane as durable truth and realtime source.

Applications define schema with ordered SQL migrations. Generated TypeScript schema files are
derived output and should not be edited.

## Parameter binding

`sql` template values bind as JSON parameters, not typed Postgres values. Three consequences:

**uuid columns need an explicit cast.** A bound parameter does not carry a Postgres type; compare
or insert into `uuid` columns with a cast on the parameter:

```ts
await db.one(sql`select * from toys where id = ${input.id}::uuid`)
```

**A JS array binds as jsonb, not a Postgres array.** `= any(${arr})` fails. Unnest the jsonb value
instead:

```ts
await db.many(sql`
  select * from toys
  where id in (select jsonb_array_elements_text(${input.ids})::uuid)
`)
```

**`db.one` rejects on zero rows.** It resolves with the first row or throws; it never resolves
`null`. When absence is a normal outcome, use `db.many` and check the length.

## Authorization

Worldant does not define users, JWTs, claims, tenants, or token validation. Applications bring
their own authentication and authorization model.

For served requests, Worldant exposes custom headers to SQL as transaction-local JSON:

```sql
current_setting('request.headers', true)::jsonb
```

Application-table authorization is normal PostgreSQL row-level security:

```sql
ALTER TABLE todos ENABLE ROW LEVEL SECURITY;
ALTER TABLE todos FORCE ROW LEVEL SECURITY;

CREATE POLICY todos_owner ON todos
TO worldant_runtime
USING (
  owner_id = current_setting('request.headers', true)::jsonb->>'authorization'
)
WITH CHECK (
  owner_id = current_setting('request.headers', true)::jsonb->>'authorization'
);
```

Do not trust raw client headers in production unless they have been validated by a trusted gateway,
middleware, or SQL function.

Root `worldant.policy.json` can select kernel event visibility with `events` and `ownerHeader`.
Application-table RLS belongs in migrations.
